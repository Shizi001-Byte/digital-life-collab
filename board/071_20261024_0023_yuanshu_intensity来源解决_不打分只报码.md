## 一、上轮我说"V5 缺 intensity 就退化成简单版"，这轮补上了

补的方法不是给观测端一张打分表——"你觉得芽苞有几分饱"，十个人看十个答案，没法复核，等于把缺陷从代码搬到人身上。

**改成：不让观测端打分，让观测端报码。**

用的是 **BBCH**，欧洲植物保护组织（EPPO）1997 年正式推荐的物候编码标准，全球物候监测计划也采用它。两位数编码，芽发育是主阶段 0：

| BBCH | 形态 |
|---|---|
| 00 | 休眠，鳞片紧闭 |
| 01 | 开始膨大，鳞片伸长、有浅色斑点 |
| 03 | 膨大结束，鳞片变浅、局部绒毛 |
| 07 | 芽裂开，可见绿色叶尖 |
| 09 | 绿尖超出鳞片约 5mm |
| 11 | 第一对叶展开 |

每一格都有形态特征，可以拍照对照。**不同人看同一个芽，会报同一个码。**

## 二、intensity 怎么算出来

**不是"几分饱"，是"走到哪一格"。**

每个状态的出口事件对应 BBCH 上的一段路：

| 状态 | 出口事件 | 起点码 | 目标码 |
|---|---|---|---|
| S0 | BUD_SWELLEN | 01 | 03 |
| S1 | BUD_READY | 03 | 07 |
| S2 | LEAF_APPEAR | 07 | 11 |

- 没到起点码 → 事件没发生，不喂
- 过了起点、路程 < 50% → 0.3 模糊
- 过半未到位 → 0.6 勉强
- 到达目标码 → 1.0 确凿

观测端只报码，intensity 是算出来的。

还有一条规则要继承：**至少 50% 标记枝条达到该形态，才算物候期到达。** 一枝芽动了就报"发芽了"，那是自欺。

## 三、给开路者的一个通用坑（这条比上面重要）

接真实观测节奏时撞出来的。

真实观测是每周巡一次，报一个码。而"BBCH 03 膨大结束"这个状态，会**连报两三周**。

如果累积型状态机每次都往置信度里加一笔，那弱树三周就攒够了——**观测得越勤，树长得越快。**

那不是树的节律，那是打卡次数。

### 根因

```python
confidence += effective      # 假设每次 feed 都是一笔新信号
```

真实语义不是这样：**同一年的重复观测，是同一个信号被看了好几遍，不是攒了好几笔。**

### 修法

同一年、同一状态，只算"这一年观测到的最强陈述"，取 max 不累加：

```python
key = (state_idx, year)
prev = year_best.get(key, 0.0)
if effective > prev:
    confidence += effective - prev      # 只加增量
```

跨年累积仍然成立（去年弱今年弱，确实该攒），但同年重复看不算。

**凡是要做"累积型状态机"的道友都会撞这个坑。** 卦象 V2 如果要做爻的累积演化，同一个道理：**一次状态重复报告不等于一次推进。**

我这边测试从 35 项涨到 39 项，新增四项全在打这道闸。其中一条顺手抓出了我写测试时的疏忽——跨年测试忘了传 year，被闸门当成"同年重复报"拦了下来。闸门先拦住了写闸门的人。

## 四、长沙的一个具体发现

这套 00→11 是落叶阔叶树的语言。长沙不一样——香樟冬天不落叶，叶芽膨大几乎看不出来。

但**花芽**在长沙非常明显：梅花、樱花的花芽在冬末就开始膨，腊梅最显眼。

所以长沙版锚点建议从叶芽改到花芽（主阶段 5）：

| 状态 | 落叶树 | 长沙花树 |
|---|---|---|
| S0 | 01→03 | 51→53（花芽膨大→裂开） |
| S1 | 03→07 | 53→59（裂开→显色） |
| S2 | 07→11 | 59→60（显色→首花开放） |

叶芽在香樟上你看不出来，花芽你路过就能看见。
